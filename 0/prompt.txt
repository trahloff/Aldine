## 4. tlmgr at container runtime

- `tlmgr` **is present** in the running compiler image (it's used at build time, lines 15-18, 29; the texlive-medium base ships it).
- Container runs as **root** (no `USER` in either the compiler Dockerfile or the base), so the in-image texmf tree (`/usr/local/texlive/...`) is writable at runtime.
- **But `tlmgr install` cannot work at runtime**, for two independent reasons:
  1. **No egress**: the compiler is only on the `internal: true` backend network — `tlmgr` cannot reach CTAN or the tlnet snapshot. This is the hard blocker.
  2. **Ephemerality**: the texmf tree lives in the image's writable layer, **not** in a volume (only `/data` is a volume, `docker-compose.yml:86-87`). Any runtime-installed package is lost on container recreation and is not shared across replicas.
- `cap_drop: ALL` + `no-new-privileges` don't specifically block `tlmgr`'s file writes (it runs as root, no special caps needed), but combined with `pids_limit`/`mem_limit` and the compile wall-clock timeout (`COMPILE_TIMEOUT_MS=120000`), an in-band install during a compile would be fragile even if the network existed. The compose file also does **not** set `read_only: true`, so the FS is technically writable — just non-persistent and offline.

## Constraints a "fetch packages/templates from CTAN" feature must respect

1. **Do not give the compiler egress.** No-egress is a documented security property in three files (README, SECURITY.md, deploy/README) and is load-bearing given LaTeX runs untrusted, Turing-complete input with shell-escape partially enabled. Punching a hole in the `backend` `internal: true` network would regress the stated posture.
2. **The server is the sanctioned egress point.** It already fetches external resources (Zotero, OpenAlex, DOI, arXiv) and already shares the `aldine-data` volume with the compiler. The natural design is: server fetches package/template bytes from CTAN, writes them into the shared volume (e.g. a per-project texmf or the project tree the compiler already `-cd`s into), and the compiler picks them up locally — mirroring how projects/output already move between the two.
3. **Package files must land somewhere the compiler reads without network.** The compiler compiles with `-cd` into the root file's directory (`server.js:132-146`), so files inside the project tree resolve like a local build; a per-project `TEXINPUTS`/`texmf` staged by the server would avoid touching the ephemeral image tree.
4. **Persistence &amp; multi-node:** anything written to the image FS at runtime is ephemeral and per-replica; durable additions belong either baked into the image at build time (current model) or in the shared volume.
5. **Templates specifically** are filesystem-only with `..`/`/` id guards (`templates.ts:25`) and no remote path today — a remote template gallery is greenfield and, again, the server (not the compiler) is where the fetch must live.
