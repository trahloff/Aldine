# Papyr Auth / Session / User Integration Surface

## Identity model (what flows everywhere)

The canonical user record is `User` in `apps/server/src/db/types.ts:10-18`: `{ id, email, name, salt, hash, createdAt, provider? }`. Everything downstream consumes a stripped `PublicUser = { id, email, name, provider? }` (`apps/server/src/auth.ts:22`, projected by `pub()` at `auth.ts:27`). The frontend mirror is `AuthUser = { id, email, name, provider? }` (`apps/web/src/api.ts:1`).

Fields actually depended on downstream:
- **`user.id`** — project ownership (`meta.ownerId === user.id`), usage metering, GitHub connection bucket keying, session lookup.
- **`user.email`** — collaborator ACL matching (lowercased), OAuth account linking key, reset lookup.
- **`user.name`** — comment author, git commit author attribution, UI display chip.
- **`user.provider`** — distinguishes password vs OAuth accounts; gates password-change UI; enforces "same provider only" merge.

## 1. apps/server/src/auth.ts — the security core

Env/config constants:
- `AUTH_ENABLED` `auth.ts:14` — master gate (`AUTH_ENABLED=1`). When off, everything here is bypassed and every request is anonymous with full access.
- `SSO_ONLY` `auth.ts:16` (`PAPYR_SSO_ONLY=1`) — disables all password endpoints.
- `COOKIE = 'papyr_session'` `auth.ts:17` — the session cookie name.
- `SESSION_DAYS = 30` `auth.ts:18`; `RESET_TTL_MS = 1h` `auth.ts:19`.
- `SECURE_COOKIES` `auth.ts:25` — Secure flag when HTTPS.

Password hashing (custom, scrypt):
- `hashPassword` `auth.ts:29-31` — `crypto.scryptSync(password, salt, 64)`.
- `verifyPassword` `auth.ts:32-37` — timing-safe compare.

Exported functions:
- `pub(u)` `auth.ts:27` — User → PublicUser.
- `register(email, password, name?, provider?)` `auth.ts:39-56` — validates email/password, rejects duplicates, generates `id = randomBytes(9).base64url`, hashes password (empty hash for OAuth users), persists via `db().createUser`. Returns PublicUser.
- `login(email, password)` `auth.ts:58-62` — looks up by email, `verifyPassword`, throws on empty hash (OAuth accounts can't password-login).
- `getUser(id)` `auth.ts:64-66` — passthrough to `db().getUser`.
- `findOrCreateOAuth(email, name, provider)` `auth.ts:74-82` — the OAuth user-provisioning path. Merges only into an existing account of the **same** provider; otherwise errors (anti-pre-hijack). Creates a passwordless user via `register(email, '', name, provider)`.
- `changePassword(userId, current, next)` `auth.ts:84-93` — re-hashes, then `revokeUser` (sign out everywhere).
- `requestReset(email)` `auth.ts:96-102` — mints `randomBytes(24)` token, stores via `db().createReset`, returns `{token, user}` (or null; never leaks existence).
- `resetPassword(token, next)` `auth.ts:104-115` — validates token/expiry, re-hashes, deletes reset, revokes all sessions.

Session model — **server-side revocable, opaque random SID** (not a JWT):
- `createSession(userId)` `auth.ts:118-122` — `sid = randomBytes(24).base64url`, stored with 30-day exp via `db().createSession`. Returns the raw sid (which becomes the cookie value).
- `destroySession(sid)` `auth.ts:124-126`, `revokeUser(userId)` `auth.ts:128-130` (deletes all sessions for a user).
- `verifyToken(sid)` `auth.ts:132-138` — the core validation: `db().getSession(sid)` → check expiry → `db().getUser` → `pub`. **This is the single function any external provider would have to replace.**

Cookie helpers:
- `parseCookies` `auth.ts:141-149`, `sessionCookie(sid)` `auth.ts:150-152` (`HttpOnly; SameSite=Lax; Path=/; Max-Age`), `clearCookie()` `auth.ts:153-155`.
- `sidFromRequest(cookieHeader)` `auth.ts:156-158` — pulls the `papyr_session` value.
- `userFromRequest(cookieHeader)` `auth.ts:159-162` — `AUTH_ENABLED ? verifyToken(sidFromRequest(...)) : null`. **The universal "who is this request" entry point**, used by both routes and collab.

Persistence is fully abstracted behind the `DataStore` interface (`db/types.ts:70-111`), implemented twice: JSON files (`db/json.ts:52-94`) and Postgres (`db/pg.ts:73-115`, tables `users`/`sessions`/`resets` created at `pg.ts:40-50`). Auth methods needed: `createUser/getUser/findUserByEmail/updateUser`, `createSession/getSession/deleteSession/deleteSessionsForUser`, `createReset/getReset/deleteReset`.

Note: these are **login** providers, distinct from the separate GitHub-repo-sync OAuth in `github.ts` (see routes below).

## 4. apps/server/src/collab.ts — WebSocket auth (must keep working)

- `authHook` `collab.ts:75-85` — only defined when `AUTH_ENABLED` (defining `onAuthenticate` makes Hocuspocus require a token from all clients). Inside `onAuthenticate` `collab.ts:76-84`: parses the doc name → **`user = await userFromRequest(requestHeaders.cookie)`** (`collab.ts:79`) → `readMeta` → `canAccess(meta, user)`. Throws to reject.
- The real credential is the **HttpOnly `papyr_session` cookie** sent on the WS upgrade; the client-supplied `token` string is just a non-empty trigger.
- Upgrade wiring: `apps/server/src/index.ts:46-49` forwards `/collab` upgrades to `hocuspocus.handleConnection(ws, request)` (request carries the cookie header).
- Client side: `CodePane.tsx:167-177` and `editor/commentSignal.ts:20-27` open `HocuspocusProvider` at `/collab` with `token: 'papyr-session'` (placeholder). No token/JWT is sent — auth rides entirely on the cookie.

Coupling: collab depends on `userFromRequest` (cookie → PublicUser) and `canAccess`. Any provider swap must keep the session identifiable from the WS handshake's cookie header, or switch collab to a token passed in the `token` field.

## Summary: what a provider swap touches

Server chokepoints (small, well-isolated): `auth.ts` (`verifyToken`, `userFromRequest`, `createSession`, `sessionCookie`, `findOrCreateOAuth`, password fns), `oauth.ts` (whole registry), the auth routes + cookie-set sites + `onRequest`/`preHandler` hooks in `routes.ts`, and the `DataStore` user/session/reset methods (`db/types.ts:75-90`, json.ts, pg.ts).

Cross-cutting couplings that constrain any design: (a) **collab.ts authenticates via the HttpOnly cookie on the WS handshake** through `userFromRequest` — must be preserved or reworked; (b) **`authz.ts` keys ownership on `user.id` and sharing on `user.email`** — stored `ownerId` values and `share.collaborators` emails create migration coupling if identity IDs change; (c) usage metering and GitHub-sync connections are keyed on `user.id`; (d) the frontend is entirely `api.me()`-driven with no token handling, so it adapts to any cookie/session scheme without storage changes.</result>
