## What I fixed

All 15 were applied except one. Server: added `isMember` in `authz.ts` as the single membership predicate, with `canAccess` now *derived* from it (`isMember || link`) so the two can't drift, and `isListed` as its alias; `ownerName` no longer rejects. Added `requireMember`/`requireOwner` guards in `routes.ts` and applied them — owner-only for zotero link/unlink, github reset-to-remote and switch-branch; members-only for zotero search/sync, all github remote ops, PATCH project, and comment deletion (non-members may still delete their own). `publicMeta` now discloses `share.collaborators` only to the owner and exposes an `isMember` flag. The share route calls a new `closeProjectConnections` in `collab.ts`, which drops the project's collab sockets so clients reconnect and re-authenticate — revoked users are refused, allowed users resume.

Client: `Modal` keeps `onClose` in a ref and mounts its focus effect once, ending the focus-steal. `ShareModal` reuses `Pick&lt;ProjectSummary,…&gt;`, validates addresses against the server's own regex before saving (accepting `,` `;` and newlines), gained a Copy link control in link mode, grouped radios and a real label, and returns the saved project so both call sites patch state in place instead of refetching. Home gates Delete on ownership and reports failures; Editor gates Publish/sync, reverts a rejected rename, and only nudges the owner toward GitHub.

Tests: the link-sharing e2e gained positive controls (owner listed, link-mode collaborator listed — it previously passed against an empty list) plus status assertions; added one API test for the link visitor's limits and one UI test driving the editor Share button, satisfying the CLAUDE.md rule that headline features get an e2e. CHANGELOG reordered to the Added/Changed/Fixed order the file's own 0.2.0 release uses.

**Skipped:** the legacy ownerless-project hole (finding 7). Tightening `!meta.ownerId` needs a product decision — an ownership-claim flow — since making `isOwner` false there would leave pre-auth projects with no one able to share or delete them, and making `canAccess` false would lock users out of their own work. Worth deciding before the next release; it silently voids the "Invite only" promise on any project created before auth was enabled.
