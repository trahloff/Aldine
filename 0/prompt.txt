- **Two live iOS apps named Papyr**: a [document scanner](https://apps.apple.com/us/app/papyr/id6758280008) and a [PDF/audiobook reader](https://apps.apple.com/us/app/papyr-pdf-audiobooks/id6760125804) — both document-adjacent, both active (2025+). SEO for "papyr app" is contested.
- **[papyrai.com](https://www.papyrai.com/)** — "Papyr" AI education tool.
- **[Papyrus Software](https://apps.apple.com/us/app/papyrus-software/id522141912)** — large enterprise *document processing* vendor. Different name, but the closest thing to a trademark holder in an adjacent class. Low but nonzero risk.

**Verdict:** no collision in the LaTeX/dev-tools space, so keep the name — but you'll be "papyr latex" or "papyr overleaf" in search forever, never "papyr". Budget for that in SEO (repo description, site `&lt;title&gt;`: "Papyr — self-hosted LaTeX collaboration"). Renaming now would cost more than the collisions do.

**Overleaf mentions:** "Overleaf alternative" is clean nominative use — Immich/Photoprism do the same with Google Photos, and Overleaf has no history of chasing this. Two tone fixes: (a) drop the "*(Overleaf can't)*" jab (§1) — it's also *imprecise*, which is worse than mean; (b) consider one footnote-style line: "Overleaf is a trademark of its owners; Papyr is unaffiliated." ## 5. Launch-day response playbook: top 8 hostile comments

**1. "Yet another Overleaf clone. Overleaf CE exists and is free."**
&gt; Overleaf CE is genuinely good, and if it fits, use it. Papyr exists because CE's free tier excludes what my group needed — track changes, git, and Zotero are all Server Pro or premium features — and because I wanted something I can run in two containers without Mongo and Redis. Papyr's whole feature set is MIT, including review comments and git branches. Comparison table in the README, including the rows where Overleaf wins.

**2. "Why not just git + VS Code + LaTeX Workshop?"**
&gt; That's my setup too, and Papyr doesn't replace it — projects are real git repos, so you can clone one and keep using VS Code, and pushes show up in the web editor. Papyr is for the other people on the paper: the co-author who won't install a TeX distribution, the advisor who wants to leave comments in the browser. It's a web front-end on a workflow you already like, not a walled garden replacing it.

**3. "MIT? Overleaf is AGPL — did you copy code?" / "MIT means AWS eats your lunch."**
&gt; No Overleaf code — different language, stack, and architecture (Node/Fastify + Yjs CRDTs + git worktrees vs. their Mongo-backed OT). On MIT vs AGPL: I picked maximum adoption on purpose. If a cloud vendor hosts Papyr, self-hosters still got a free tool and I lost nothing I was counting on — this isn't a company protecting a moat.

**4. "Cool, another AI-built repo that'll be abandoned in six months." (sustainability/bus factor)**
&gt; Fair — most side projects die, and I can't promise mine won't. What I can point to: a Playwright e2e suite covering compile, collab, branches, and plugins that gates every change; CI plus tagged GHCR releases; and I use it for my own papers, which is the strongest predictor of maintenance. And since projects are plain git repos on a volume, abandonment leaves you with… your git repos. The exit cost is `git clone`.

**5. "Why is there AI in my LaTeX editor?" / "AI error fixing is a gimmick."**
&gt; It's off unless you set an API key, invisible otherwise, and the key never reaches the browser. It does one narrow thing: when a compile fails, it turns LaTeX's famously hostile logs into a plain-English diagnosis with a proposed patch you can reject. If you can read `! Undefined control sequence` fluently you don't need it; your co-authors probably can't. Delete the env var and Papyr is a 100% AI-free editor.

**6. "Self-hosting a LaTeX compiler is an RCE service with extra steps."**
&gt; This was designed for, not bolted on. The compiler container runs on an internal-only Docker network with no internet egress, drops all Linux capabilities, and is capped on CPU/memory/PIDs. LaTeX runs with restricted shell-escape (whitelist) and `openin_any=p`, compiles are rate-limited and concurrency-capped. Threat model is in SECURITY.md — I'd genuinely welcome someone trying to break it, that's a review I can't buy.

**7. "'Slim'? The TeX Live container is gigabytes." / "'No Redis' but SCALING.md says use Redis."**
&gt; Both fair. TeX Live is inherently heavy — "slim" means operational surface (two containers, flat-file storage, no DB to migrate or babysit), not image size; I should say that more precisely. And yes: Postgres and Redis are the documented *opt-in* path for multi-node. The default single-box deploy uses neither, and I'd rather document the scaling walls honestly (docs/SCALING.md) than pretend they don't exist.

**8. "Most of this was written by Claude. Why should I trust any of it?"**
&gt; Yes — disclosed in the first comment (or title). I directed, reviewed, and tested; the agent wrote most of the code. My trust argument isn't "trust the author," it's the same as for any codebase: an e2e suite that exercises every headline feature in a real browser, a sandboxed compiler, a security review pass, and a live instance you're welcome to poke at. Judge the artifact, not the typist — the repo makes that unusually easy.
