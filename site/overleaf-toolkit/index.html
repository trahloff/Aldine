Installing Overleaf Community Edition with the Overleaf Toolkit

The Overleaf Toolkit is how Overleaf itself tells you to run Community Edition on your own server. You clone it, run bin/init, edit two config files, run bin/up and register the first admin at /launchpad. This guide walks through those steps with the commands exactly as Overleaf documents them, then covers TeX Live packages, upgrades and backups, which is where most of the ongoing work is.

Written by the Aldine project, so read it with that in mind. Statements about other products are taken from the linked pages of that product's own documentation. Checked on 24 November 2026.

What the Toolkit is

It is Overleaf's own repository, github.com/overleaf/toolkit, licensed under the GNU Affero General Public License v3. The README calls it "the standard tools for running a local instance of Overleaf", for Community Edition and for Server Pro alike. (Overleaf Toolkit README, as of November 2026) Under the hood it is a set of bash scripts in bin/ that wrap docker compose. Overleaf's on-premises docs call it the "recommended way" to deploy and manage both editions. (Overleaf docs: using the Toolkit, as of November 2026)

The steps below come from Overleaf's documentation, and the credit is theirs; this page puts them in one place. If you are still deciding between Community Edition, Server Pro and something else, the feature comparison is on self-hosting Overleaf: what Community Edition includes. This page assumes you have decided and want it running.

Requirements

The Toolkit itself needs two programs: bash and Docker. (Overleaf Toolkit docs: quick start, as of November 2026) Overleaf's software requirements add the details. (Overleaf docs: software requirements, as of November 2026)

  • Overleaf "highly recommend[s]" a Debian-based system such as Ubuntu.
  • Supported dependency versions are "Docker 25.0 and 29", "MongoDB 7.0 and 8.0" and "Redis 6.2 and 7.5".
  • You don't install MongoDB or Redis yourself. Docker Compose pulls them, unless you configure an existing installation.

Before starting, both of these should run without an error:

docker --version
docker compose version

For hardware, the documented baseline is "2 cores and 3GB memory" for "around 5 concurrent users", plus "1 CPU core and 1GB of memory" for every 5 to 10 more. Concurrent is the word that matters; registered users do not count. (Overleaf docs: hardware requirements, as of November 2026)

The Toolkit is tested on Ubuntu Linux, and other platforms "are not officially supported". On macOS, Overleaf suggests brew install coreutils to get a working realpath. (Overleaf Toolkit docs: dependencies, as of November 2026)

Install, step by step

1. Clone the Toolkit

Overleaf recommends cloning into your user's $HOME directory to avoid permission problems. (Overleaf docs: download the Toolkit, as of November 2026)

git clone https://github.com/overleaf/toolkit.git ./overleaf-toolkit
cd ./overleaf-toolkit

Run every later command from this directory.

2. Create the configuration

bin/init
ls config

You should see three files: overleaf.rc, variables.env and version. bin/init does not overwrite configuration files that already exist, so running it twice is harmless. (Overleaf docs: initialize the configuration, as of November 2026)

By default the Toolkit uses Community Edition. Nothing to switch. (Overleaf Toolkit docs: quick start, as of November 2026)

3. Fill in variables.env

Before the first start, Overleaf's install guide has you set three variables in config/variables.env: (Overleaf docs: personalizing your instance, as of November 2026)

  • OVERLEAF_SITE_URL, the public address of the instance. It is used in links and for the websocket connection, and the docs say it "must be configured correctly".
  • OVERLEAF_EMAIL_FROM_ADDRESS, the sender of outgoing mail.
  • OVERLEAF_ADMIN_EMAIL, where users reach whoever runs the site.

4. Start it

bin/up

This downloads the images, creates the containers and starts them with the log output attached. CTRL-C stops the services; bin/start starts them again without attaching to the logs. When it's up, the login page is at http://localhost/. (Overleaf docs: personalizing your instance, as of November 2026) (Overleaf Toolkit docs: quick start, as of November 2026)

A running install has three containers, named sharelatex, mongo and redis in Overleaf's example output. (Overleaf docs: software requirements, as of November 2026)

5. Create the first admin account

Open http://localhost/launchpad, enter the email and password you want for the administrator, and click Register. Then log in at http://localhost/login and click the green button on the welcome page. From http://localhost/project you can create a first example project, which opens the editor next to a PDF preview. (Overleaf docs: post-installation tasks, as of November 2026)

The configuration files

All of your configuration lives in config/, which git ignores, so updating the Toolkit code leaves it alone. (Overleaf Toolkit docs: configuration overview, as of November 2026)

overleaf.rc holds the top-level settings as VARIABLE_NAME=value lines. The ones you are likely to touch first: (Overleaf Toolkit docs: overleaf.rc, as of November 2026)

  • OVERLEAF_LISTEN_IP, default 127.0.0.1. With the default, the site is reachable only from the host itself. For direct access from other machines it must be the host's public IP. Combined with the TLS proxy, 0.0.0.0 or the external IP "will typically cause errors".
  • OVERLEAF_PORT, default 80.
  • OVERLEAF_DATA_PATH, the host directory for compile data and project files. Docker writes there as root, so expect root-owned files. (Overleaf Toolkit docs: persistent data, as of November 2026)

variables.env is loaded into the container as environment variables: the application name shown in the header, email settings, and so on. version holds the Docker image version. An optional config/docker-compose.override.yml is passed to docker compose too. (Overleaf Toolkit docs: configuration overview, as of November 2026)

Easy to miss: a config change does not reach a container that is merely stopped and started with bin/stop and bin/start; you need bin/up (or bin/up -d). Overleaf recommends bin/docker-compose down followed by bin/up after editing overleaf.rc or variables.env. And bin/backup-config -m zip ~/overleaf-config-backup.zip saves the whole directory. (Overleaf Toolkit docs: configuration overview, as of November 2026)

For HTTPS, the Toolkit ships an optional NGINX proxy. bin/init --tls generates its config and a sample certificate in config/nginx/; you replace the sample with your own certificate, set NGINX_ENABLED=true in overleaf.rc and re-run bin/up. (Overleaf Toolkit docs: quick start, as of November 2026)

TeX Live packages

To save bandwidth, the image "only come[s] with a minimal install of TeX Live". A paper that needs a package outside that install will not compile until you add it. On Community Edition you add packages with tlmgr inside the container. (Overleaf docs: upgrading TeX Live, as of November 2026)

bin/shell
# now inside the sharelatex container:
tlmgr install scheme-full
tlmgr path add

scheme-full is the complete TeX Live. You can also install single packages, for example tlmgr install tikzlings tikzmarmots tikzducks. Since release 3.3.0, tlmgr path add is required after every tlmgr install so the binaries land on the system path.

Those changes are ephemeral. They vanish the next time Compose recreates the container, which happens whenever you change the config. To keep them, Overleaf's docs commit the container to a new image and point config/version at it:

cat config/version
# 6.1.1
docker commit sharelatex sharelatex/sharelatex:6.1.1-with-texlive-full
echo 6.1.1-with-texlive-full > config/version
bin/up -d

Use your own version number in place of 6.1.1, which is Overleaf's example. You repeat all of this after every upgrade to a new Overleaf version. (Overleaf docs: upgrading TeX Live, as of November 2026)

Upgrades

The Toolkit is a git repository, and bin/upgrade does the work. It first offers to update the Toolkit code. If the default image version has changed, it then offers to update config/version, and if you accept it shuts the services down, takes a backup and starts them again. The old version file is kept as config/__old-version. (Overleaf docs: upgrading your deployment, as of November 2026)

Three warnings from the same page are worth reading before you press yes:

  • Take a consistent backup before every major and minor upgrade.
  • "Downgrading is not supported." Upgrades run one-time database migrations, so the way back is restoring the pre-upgrade backup, not editing config/version.
  • Never skip a major version. If you are more than one major version behind, Overleaf says you must not use bin/upgrade and should upgrade step by step instead, checking the release notes for extra steps on the way.

Updating the Toolkit code alone does not change the image you run, so that part is low-risk.

Backups

Data lives in three places: MongoDB (users and projects), Redis (sessions and in-flight edits) and the Overleaf filesystem under OVERLEAF_DATA_PATH (uploaded files and history). A consistent backup needs all three, taken while nobody can edit. (Overleaf docs: data and backups, as of November 2026)

bin/docker-compose stop sharelatex
# back up MongoDB (e.g. with mongodump), the data directory (e.g. with rsync)
# and Redis, then:
bin/docker-compose start sharelatex

Redis uses append-only-file persistence by default on new Toolkit installs. Overleaf advises keeping backups on a separate server, ideally somewhere else entirely, and testing them. For moving a whole instance to a new server, the same page gives a recipe: bin/stop, then a tarball of config/ and data/, copied across and unpacked before bin/up. (Overleaf docs: data and backups, as of November 2026)

When something does not work

Run bin/doctor first. It reports the host, checks dependencies and your configuration, and ends with a list of warnings. Overleaf asks for its output in bug reports. Logs come from bin/logs -f web, or several services at once with bin/logs -f filestore docstore web clsi. (Overleaf Toolkit docs: quick start, as of November 2026)

On macOS or Windows, MongoDB can fail to restart with "Failed to start up WiredTiger under any compatibility version". The documented fix is to keep the MongoDB and Redis data in Docker volumes via config/docker-compose.override.yml instead of bind-mounted directories. (Overleaf Toolkit docs: persistent data, as of November 2026)

Help for Community Edition comes from the community, through GitHub issues on the Toolkit repository. (Overleaf Toolkit README, as of November 2026)

What Community Edition does not include

Overleaf's comparison table marks commenting, real-time track changes, git integration, the symbol palette, SSO via SAML 2 and LDAP, and sandboxed compiles as Server Pro features, among others. (Overleaf docs: Server Pro vs. Community Edition, as of November 2026) The full list, with what it means in practice, is on our comparison page.

One of those rows changes how you should run the install. Sandboxed compiles, also called sibling containers, compile each project in its own container. Overleaf states they "are not available in Community Edition, which is intended for use in environments where all users are trusted". Without them, a compile has full read and write access to the sharelatex container's filesystem, network and environment variables. (Overleaf Toolkit docs: sandboxed compiles, as of November 2026) Overleaf adds that Community Edition "is not appropriate for scenarios where isolation of users is required."

If you outgrow Community Edition, Overleaf describes Server Pro as "a drop-in replacement". With a licence and the quay.io credentials Overleaf supplies, you set SERVER_PRO=true in config/overleaf.rc and the next bin/up pulls the Server Pro image. (Overleaf docs: choose Community Edition or Server Pro, as of November 2026)

The same in Aldine

Aldine is a separate open-source project (AGPL-3.0), a self-hosted collaborative LaTeX editor, not related to Overleaf. For comparison, here is how the steps above map onto it. The details are on self-hosting Aldine with Docker Compose.

  • Install. Save the compose file from that guide as docker-compose.yml and run docker compose up -d. No clone, no init script; it is two containers (app and compiler) and no database server, and the instance answers on http://localhost:8080.
  • First admin. There is none at first, because login is off by default (single-tenant). AUTH_ENABLED=1 turns on accounts, and ALDINE_ADMIN_EMAILS opens the /admin page.
  • TeX Live. The compiler image carries TeX Live's medium scheme plus extra collections; the first pull is about 2.4 GB. A -full image with all of TeX Live is one setting away (ALDINE_TEXLIVE=-full), so there is no docker commit step to repeat after upgrades.
  • Upgrades. The version is pinned in .env. Change it, then docker compose pull && docker compose up -d.
  • Backups. deploy/backup.sh and deploy/restore.sh in the repository, with a systemd timer for daily snapshots.
  • Compile isolation. Always on: the compiler has no internet access, drops all Linux capabilities and is limited in memory and processes.

The limits are those of a young project. The first release was in July 2026 and 1.0 in October 2026. Aldine is self-hosted only, supports one app node, and has review comments with suggested edits rather than keystroke-level track changes. The rest is in the list of limits.

When the Toolkit is the better choice

  • Your users know Overleaf and you want the same editor on your own hardware.
  • You may need Server Pro later. The Toolkit runs both editions, and switching is one setting once you have a licence. (Overleaf docs: choose Community Edition or Server Pro, as of November 2026)
  • You need SAML or LDAP sign-in, or vendor support. Server Pro documents both, and Aldine offers neither SAML nor LDAP.
  • You want a long track record. Overleaf dates from 2011 (Overleaf: about, as of November 2026); Aldine's first release was in July 2026.

Common questions

What is the Overleaf Toolkit?

It is Overleaf's own repository of scripts for running Overleaf on your own server, published at github.com/overleaf/toolkit under the AGPL-3.0. The scripts wrap docker compose, and the same Toolkit runs both Community Edition and Server Pro.

Which port does Overleaf Community Edition listen on?

Port 80 on 127.0.0.1 by default. OVERLEAF_PORT and OVERLEAF_LISTEN_IP in config/overleaf.rc change that; for direct access from other machines, the listen IP has to be the host's public address. Overleaf's docs say 0.0.0.0 or the external IP will typically cause errors together with the bundled TLS proxy.

How do I get the full TeX Live in Overleaf Community Edition?

Open a shell with bin/shell, run tlmgr install scheme-full and then tlmgr path add, and save the container as a new image with docker commit. Put the new tag in config/version and run bin/up -d. You repeat this after every upgrade.

Can I run the Overleaf Toolkit on macOS or Windows?

The Toolkit is tested on Ubuntu Linux and other platforms are not officially supported. On macOS, Overleaf suggests installing GNU coreutils for realpath, and on macOS or Windows the MongoDB data may need a Docker volume instead of a bind mount.

Can I switch from Community Edition to Server Pro later?

Yes. Overleaf describes Server Pro as a drop-in replacement. With a licence and the registry credentials Overleaf supplies, you set SERVER_PRO=true in config/overleaf.rc and run bin/up.
